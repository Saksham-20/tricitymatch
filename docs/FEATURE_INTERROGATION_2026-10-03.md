### CHAT-01: Chat REST + group chat (message content handling) 🟠
- **Question:** If I type "I'm free on Sunday & Monday", what does the other person actually see? *(member)*
- **Finding (bug):** The server HTML-escapes message text before storing it (& to &amp;, ' to &#x27;, " to &quot;, < and > to entities, and anything shaped like <...> is deleted outright). No client decodes it. Web renders sanitizeText(content) as a React text child, and mobile renders {msg.content} raw, so entities show literally. Edit pre-fills the escaped text and re-escapes on save, so it compounds (&amp;#x27;). Group messages use an identical sanitizer.
- **Evidence:** backend/controllers/chatController.js:44-57 (sanitizeMessage) and groupController.js:23-33; frontend/src/components/chat/MessageBubble.jsx:251 `{sanitizeText(message.content)}`; mobile/src/features/chat/ChatThreadScreen.tsx:437 `{msg.content}`; Chat.jsx:451 startEditing uses message.content. Ran DOMPurify+jsdom against the real sanitizer: "Tom & Jerry" shown as "Tom &amp; Jerry", "I'm 5 > 3" shown as "I&#x27;m 5 &gt; 3", "a<b and c>d" stored as "ad". grep for any entity decoding in frontend/src, mobile/src, shared/src found none. Dev DB has 0 escaped rows only because seed text has no apostrophes.
- **Impact:** Nearly every real English message contains an apostrophe or ampersand, so threads read as garbled text to both sides on web and app, and edits get progressively worse. Text containing < or > silently loses content.

## Features that held up

Interrogated and found solid. Listed so that no finding is not mistaken for no look.

### AUTH: Accounts and authentication

- OTP store (otpStore.js) - crypto.randomInt codes, HMAC-hashed at rest, atomic INCR attempt counting before comparison and atomic take on success
- Signup OTP proofs - single-use, bound to the verifying caller, never persisted in the web draft, drafts reset the verified flags on reload
- Login lockout key (H-2 fix) - loginLookupKey shared by check and record, constant error text, lockout works (5 failures -> 429 on own instance)
- Password reset token - single-use via password fingerprint, missing claim fatal, all sessions revoked on reset, security alert sent
- Google sign-in link to an unverified-email account - drops the squatter's password and revokes sessions; MFA accounts refuse the Google shortcut
- TOTP implementation - AES-GCM encrypted secret, per-step replay protection, hashed recovery codes, User.toJSON strips mfaSecret/recovery hashes/consent/lifecycleMail/inviteToken/fcmTokens
- Age policy - 21 men / 18 women / 21 other / 21 unknown enforced at signup (probed boundary dates), IST calendar age, profile update and admin path share one helper
- Identity lock - DOB/gender locked after onboarding, BasicInfo warns before the lock, admin change needs a reason of 10+ chars and is audited and age-checked
- Data export and deletion re-authentication - password or fresh Google credential bound to the same Google id, sensitiveActionLimiter, audit rows
- Scheduled deletion and pause - schedule/cancel/resume probed end to end (profile hidden, interests blocked, resume refused while scheduled, cancel restores), daily erasure job isolated per account
- Phone uniqueness - partial unique index users_phone_unique plus conflict handling at signup; email case/Gmail-variant lookup candidates prevent duplicate accounts
- Email change - code bound to member+address, per-member send budget, password re-auth for password accounts, availability re-checked at verify
- Email unsubscribe - signed HMAC link, GET never acts (scanner-safe), RFC 8058 POST, atomic ledger merge, page states clear and scope stated honestly
- Admin seeder production guard - refuses the published default password and weak passwords in production
- Consent evidence - termsAccepted must be asserted in the request, consent record keeps ip/UA/version history, re-acceptance requires the current version
