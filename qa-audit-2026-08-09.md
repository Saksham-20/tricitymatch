## Findings

### F-001 · CRITICAL · Auth lockout for innocent users (FIXED)
`authLimiter` = 5 req / 10 min **keyed by IP**, counting **successful** requests, shared by `/auth/login`, `/auth/refresh`, `/auth/google`.
- Repro: 4 normal logins + 1 page load from one IP → `429` on **both** refresh *and* login for ~10 min. Verified live.
- Impact: `/auth/refresh` fires automatically every ~15 min per active session. Behind mobile CGNAT / office / college wifi (the norm for a hyperlocal Chandigarh product) **all users share one IP** → a handful of legitimate sign-ins locks everyone out of logging in.
- Fix: `backend/middlewares/security.js` — `authLimiter` now `skipSuccessfulRequests: true`, max 20 **failed** attempts; new `refreshLimiter` (60/10min, own budget) applied to `/auth/refresh` in `backend/routes/authRoutes.js`.
- Retest: 8 successful logins → all 200; 8 refreshes → all 200; 6 bad passwords → 429 at #6 (per-account lockout intact); **other users on the same IP unaffected** (200).

### F-002 · CRITICAL · False "end-to-end encrypted" claim (FIXED)
Homepage asserted E2E encryption **6×** (incl. FAQ "Is my data private?" and "encrypted in transit **and at rest**").
- Reality: `Messages.content` is `TEXT`, stored **plaintext** (verified by reading rows out of Postgres); zero crypto anywhere in `chatController` / `Message` model / `socketHandler`.
- Risk: material misrepresentation of a security property to users about intimate personal conversations (DPDP Act 2023 / consumer-protection exposure), and it misleads users into sharing more than they would.
- Fix: `frontend/src/pages/Home.jsx` — all 6 claims → "encrypted in transit", "private conversations". No other file made the claim.
- **Open recommendation:** if E2E is desired as a product feature, it must actually be built; otherwise keep copy as-is.

### F-003 · MAJOR · Support enquiries were a black hole (FIXED — feature built)
`ContactMessage` rows were **written and never read**: no admin route, no UI, no nav entry; `status` enum (`new/read/resolved`) permanently dead. Only other delivery was a best-effort email on a config-gated channel (off in dev, SMTP still TODO in prod). Model comment even claimed "so support always has the record".
- Evidence: 6 real enquiries sat unseen in DB, oldest from 04 Jul 2026.
- Fix: `GET/PUT /api/v1/admin/contact-messages` (`adminController` + `adminRoutes`), new `frontend/src/pages/admin/AdminContactMessages.jsx`, route in `App.jsx`, "Support Inbox" nav in `AdminLayout.jsx`. Paginated, status filter, search, expandable body, status change, mailto reply, unread count, 4 states.
- Retest: list renders 6, expand shows body, status→resolved persists to DB, filter returns 1, invalid status → 400, member → 403.

### F-004 · MAJOR · Unverifiable / inflated marketing claims (FLAGGED — owner decision)
Homepage hardcodes: **"1190+ marriages made"**, **"50K+ verified members"**, **"92% reply within 48 hrs"**, **"15yr serving Tricity families"**, city counts **28K/14K/8K**, plus three named parent testimonials ("Mrs. Harpreet Kaur" etc.).
- Reality in DB: 56 profiles, 4 verifications, 1 published success story. No reply-rate metric is tracked at all.
- Not auto-changed: these are business/legal calls, not defects. Recommend either wiring real counts or dropping the numbers — as written they are misleading advertising under the Consumer Protection Act 2019.
- Related: badge "Every profile manually reviewed by our safety team" / "Selfie verification before any profile goes live" — verification is optional and profiles go live unverified.

### F-005 · MINOR · Stale brand in DB content (FIXED in dev)
Published success story read "We matched on **TricityShadi**" — rendered on `/` and `/success-stories`. Rename commit `57762c9` covered code only.
- Fix: updated both `SuccessStories` rows in dev DB. **Prod action required:** same `UPDATE` must be run on production.

### F-006 · CRITICAL · Global API limiter keyed by IP → random forced logout (FIXED)
`app.use('/api', apiLimiter)` (`server.js:187`) runs **before** any route-level auth, so `req.user` was always undefined and the default keyGenerator fell back to **IP** for every authenticated request. Budget: 200 req / 15 min.
- Repro (live): a plain 12-page walk as one logged-in member exhausted it → `429` on `/api/astrologers`, then `429` on `/api/auth/me` → client treated it as session loss and **bounced the user to `/login?returnTo=…` mid-session**.
- Impact: this SPA fires 5–8 calls per page, so a single member blows 200/15min in normal browsing. Behind shared NAT every member drew from **one** bucket — the app becomes unusable within minutes for a whole office/campus/carrier.
- Fix: `apiLimiter` now keys on the verified `accessToken` (`user:<id>`), falling back to IP only for anonymous traffic; ceiling raised to 900/15min per user.
- Retest: 250 consecutive authenticated calls → **250×200, zero 429**; a second user and anonymous traffic on the same IP each keep independent buckets.

### F-007 · MAJOR · Any transient `/auth/me` failure logged the user out (FIXED)
`AuthContext.checkAuth` cleared user state on **every** error, not just `401` — so a 429, a 5xx, or a dropped connection destroyed the client session.
- Fix: `frontend/src/context/AuthContext.jsx` — only a definitive `401` clears state; other failures retry once after 1.2 s then leave the session untouched (cookie + auth hint preserved, so the next navigation recovers).
- Retest: full 14-route member walk → all land correctly, `/payment/history` no longer redirects to login.

### F-008 · MAJOR · Rate-limit factory silently dropped skip options (FIXED)
`createRateLimiter` whitelists the options it forwards, so `skipSuccessfulRequests` / `skipFailedRequests` passed by callers were **discarded**. This is what made the limiters count successes in the first place, and it silently defeated the first version of the F-001 fix (which appeared to pass only because the max had also been raised).
- Fix: factory now forwards both flags explicitly.
- Retest: 10 invalid signups consume **zero** budget (real signup after them → 201); 25 successful logins → zero blocked; 5 bad passwords still lock the **account** (429 on attempt 6, correct password rejected while locked) while other users on the same IP stay at 200.

### F-009 · MAJOR · Signup blocked by typos (FIXED)
`signupLimiter` was 3/hr/IP counting **rejected** attempts — three mistyped emails locked a genuine user, and everyone sharing their IP, out of registering for an hour.
- Fix: `skipFailedRequests: true`, max 5 real creations/hr (families commonly register together).

### F-010 · MAJOR · Password reset self-lockout (FIXED)
`/auth/forgot-password` and `/auth/reset-password` shared one 3/hr/IP budget. Requesting a reset then mistyping the new password twice locked the user out for an hour **while holding a valid token**.
- Fix: request limiter raised to 5/hr; new `passwordResetSubmitLimiter` (20 **failed**/hr, own budget) on `/auth/reset-password` — it is token-gated, not a spray surface.
- Retest: two rejected weak passwords → `400,400`; correct password → `200`; token reuse → rejected (single-use); old password → `401`, new password → `200`.

### Clean in C2 / C9 (security)
- **No user enumeration**: login returns identical `Invalid credentials` for existing vs unknown email; `forgot-password` returns the same generic message either way. Dev-only `resetToken` echo is `config.isDevelopment`-gated, as is the error `stack` — both correctly absent in production.
- **All 16 protected endpoints** return `401` unauthenticated.
- **Role matrix correct**: member and marketing both `403` on all 7 admin endpoints; member `403` on all marketing endpoints; admin reaches both.
- **IDOR probes all denied**: editing/deleting another user's message `403`, another user's notification `404`, another user's invoice `404`, reading a third-party conversation `403` — target message verified unmodified in DB.
- **No mass assignment**: `PUT /profile/me` with `role:"admin"`, `userId`, `isVerified`, `profileBoost` → role unchanged, no privileged columns exist to set; self-granting a subscription via the admin route → `403`.

### Clean in C1
`/ /about /contact /safety /terms /privacy /success-stories` + 404 all render, correct per-page `<title>`, skip-to-content link present, **zero console errors** on a genuine first visit. Contact form: client validation fires per-field, valid submit persists exactly **1** row under a double-click, success state renders. Homepage "0+/0K+" stats and blank parents section in full-page shots are the documented CountUp/whileInView artifact, **not** bugs.

### F-011 · MINOR · Admin sidebar badge read "TS" (FIXED)
Post-rename leftover: `AdminLayout.jsx` logo mark showed **TS** (TricityShadi) beside the word "TricityMatch" → now **TM**.

### F-012 · MINOR · Integration test mock was brittle (FIXED)
`tests/integration/auth.test.js` hand-listed the security middleware it mocked, so adding any limiter to the real module broke the whole suite with `Route.post() requires a callback function but got [object Undefined]`. Replaced with a Proxy that resolves any `*Limiter` export to a pass-through. Suite failures **10 → 5**.

# ROUND 2 — remaining chunks (C3, C4, C6, C7, C11)

Covers the chunks the first pass left open. All findings below were reproduced live, fixed, and retested.

Regression after round 2: backend Jest **178/183** (same 5 pre-existing `auth.test.js` mock failures, count unchanged from baseline → no regression), frontend Vitest **60/60**, production build **green** (8.34s).

## Critical — FIXED
10. **F-014 Contact-unlock quota was not enforced under concurrency.** `unlockContact` did read-modify-write on the in-memory `Subscription` instance. Eight parallel unlocks all started from the same stale count and overwrote each other. Measured live: **11 `ContactUnlocks` rows against a counter reading 3**, so the plan cap could be blown open by anyone issuing parallel requests (trivially: a double-tap, or several tabs). Fixed with a single conditional `UPDATE ... SET used = used + 1 WHERE used < allowed`; if it affects no rows the transaction rolls back with a 403. Retested against a cap of 5: 11 parallel unlocks on distinct targets → exactly 5 succeeded, 7 × 403, counter 5, rows 5.

## Major — FIXED
11. **F-015 Duplicate taps returned HTTP 500** on `POST /profile/:id/unlock-contact` and `POST /match/:id`. The check-then-create pattern raced into the unique index; in Postgres that aborts the whole transaction, so the response was `INTERNAL_ERROR: current transaction is aborted`. Both now use `INSERT ... ON CONFLICT` (`DO NOTHING` for unlocks, `DO UPDATE` for match actions). 8 concurrent taps → 8 × 200 and **exactly one quota charge**. First attempt at this fix was wrong — `bulkCreate({ignoreDuplicates})` returns built instances whether or not a row was written, so it billed 6 unlocks for 1 contact; caught on retest and replaced with a `RETURNING`-checked insert.
12. **F-016 Deleted accounts stayed readable.** `GET /profile/:id` filtered on `Profile.isActive` but never on `User.status`, so a soft-deleted member's full profile still returned **200** to anyone holding the URL — while search correctly hid them, and while the UI promises "permanently removes your profile". Now inner-joins `User.status='active'` → 404. Live profiles unaffected.
13. **F-017 Plain-text password persisted in `localStorage`.** The onboarding draft wrote the whole form, password included, on every keystroke, and "Save & Exit" keeps the draft deliberately. An abandoned signup left the chosen password readable forever on that browser — on the shared family devices this product is aimed at, and to any XSS on the origin. Credentials are now stripped before persisting and never rehydrated (old drafts included).
14. **F-018 `GET /subscription/my-subscription` reported the newest row of *any* status.** Starting an upgrade and not paying (`pending`), or an old `cancelled` row, was returned as the member's current plan — the UI showed VIP while the server correctly granted nothing. Now returns the active, unexpired row or `free`.
15. **F-019 Astrologer bookings accepted a scheduled time in the past** — only `durationMin` was validated. A stale form created a ₹525 Razorpay order for yesterday. Now rejects non-future and >6-months-out dates.
16. **F-020 No UI existed for active sessions.** `GET /auth/sessions`, `DELETE /auth/sessions/:id` and `POST /auth/logout-all` shipped with the backend and were reachable from nothing in the web app (`logoutAll` sat unused in `AuthContext`). A member who suspects someone else is signed in on the family tablet had no way to look or to cut it off. Built the Settings → Account "Where you're signed in" section (4 states, per-device revoke, sign-out-everywhere). Verified end-to-end: 2 sessions → revoke → 1, and the revoked session's `/auth/refresh` returns 401.
17. **F-021 Search totals counted profiles that could never be returned.** Rows inner-joined `User.status='active'`; the count was a bare `Profile.count`. Suspended/deleted members inflated "N profiles found" and produced pages that always came back empty. Count now applies the same join (verified: 19 = 6+6+6+1).
18. **F-022 Live-selfie capture could hang forever.** `getUserMedia` stays pending while the permission prompt is unanswered, leaving "Starting camera…" on screen with no error, no timeout and no way forward — on the one flow that gates the trust badge. Added a 15s race with an actionable message and Try again.

## Minor — FIXED
19. **F-023 `/payment/success` congratulated anyone who opened the URL** ("Your subscription is now active") regardless of whether they'd paid. Now confirms against the server and redirects non-payers to `/subscription`.
20. **F-024 Password could be "changed" to itself** — returned success and revoked other sessions without changing anything, which is worst precisely when the reason for changing it is that the old one leaked. Now rejected.
21. **F-025 CSP `frameSrc` omitted `checkout.razorpay.com`** (only `api.razorpay.com` was allowed). Dev never shows this because Vite serves the page without the backend CSP; in production it risks the payment modal being blocked outright. Added.

# ROUND 3 — groups, realtime, admin writes, and the leftovers

## Critical — FIXED
22. **F-026 Redis was never actually used in production.** `initRedis()` bailed out unless `REDIS_URL` was set, but `docker-compose.yml` wires the backend to the redis service with `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` and never sets `REDIS_URL`. Production therefore logged *"Redis not configured, using in-memory cache"* and ran the Redis container for nothing — which meant **rate-limit counters and account-lockout state lived in process memory**: wiped on every deploy or restart, and counted separately per instance if the backend is ever scaled. The brute-force protection hardened in round 1 was resting on this. Now builds the client from host/port/password when no URL is present, gated on the existing `isConfigured()`. Verified by pointing dev at a real Redis exactly the way compose does: `daily-matches:<uid>:<date>` and `lockout:<email>` both appear in `redis-cli --scan` — neither was being written before. Dev `.env` restored to as-found afterwards (unset → still falls back cleanly to in-memory, no crash).

## Minor — FIXED
23. **F-027 Small tap targets on `/profile`** — six "Edit" links measured 41 × 18 px at 375 px, under the 24 px WCAG 2.5.8 floor. Padded to ~34 px with compensating negative margins, so nothing moved.
24. **F-005 follow-up** — the stale "TricityShadi" strings are **data only**; application source is clean (verified by grep over `backend/`, `frontend/src/`, `mobile/src/` — the only hits are in the generated `backend/coverage/` report). Dev rows fixed (3 `Notifications`). Production still needs it: `scripts/rebrand-stored-data.sql` added, idempotent, covers `Notifications` and `SuccessStories`.
25. **F-012 follow-up — the 5 stale integration tests are fixed; the backend suite is now fully green (183/183).** All five were stale-mock artifacts, not product bugs: the `RefreshToken` mock lacked `hashToken` (a 500 from inside the route read as a broken endpoint), fixtures were plain objects while the controllers call `toJSON()` / `save()` on them, and signup + login re-read the user via `findByPk`, which was unmocked. Added an `asInstance()` fixture helper and mirrored every static the controller calls. One test — "should reject login with wrong password" — was passing for the wrong reason: its fixture had no `password`, so it tripped the OAuth-only branch and never reached the password comparison. It now tests what it claims.

## Verified clean in round 3
**Family-group authorization** — every outsider operation on someone else's group returns 403 (read, list messages, post, add member, edit message, delete message, delete group); the previously-noted IDOR is closed. A legitimate member can read, post, and edit their **own** message, and is refused on editing or deleting another member's message, deleting the group, and removing the owner; after leaving, access drops to 403. **Socket.io realtime** — verified between two live browser sessions: a message sent by one appeared in the other with no reload. **Chat gating** — messaging a non-mutual profile is refused on both send and thread read; self-send and empty messages rejected. **Admin write paths** — user status changes (ban → login 403, profile 404, live session revoked **immediately** on the next request, restore → login 200), plan grants, report status updates, success stories (publish → appears on the public page, draft → disappears, delete), referral codes (create / duplicate 409 / toggle), marketing users (create / duplicate 409 / deactivate / stats). Invalid enum values are rejected on every one of them.

**One correction:** I flagged `PUT /admin/users/:id/status` as rejecting `suspended`. That is not a defect — this system's statuses are `active | inactive | banned | pending`, and the UI constant and the backend validator agree. My probe used a value that does not exist. Banning is the moderation action and it works end-to-end.
